A small guardrail for AI tool changes

Review the change.
Not just the code.

A tool definition changes, and suddenly a caller breaks, a prompt gets expensive, or a description starts asking for the wrong thing. ToolRatchet helps catch those changes before merge.

01 — What gets checked

Three questions before a tool ships.

Keep the review grounded in the things that actually change when teams evolve their tool surface.

01

Will existing callers still work?

Compare schemas, required fields, enums, bounds, references, tool names and removals. When compatibility cannot be established, surface the case for review instead of pretending to know.

02

Did the context budget jump?

Track token estimates for individual tools and the overall surface. Set limits or cap growth so a seemingly small description edit does not quietly inflate the prompt.

03

Did the tool text get riskier?

Flag suspicious instruction overrides, concealment language, hidden Unicode, possible exfiltration wording, credential-file references and changes to tool hints.

02 — Quick start

Start locally. Add it to CI when it helps.

ToolRatchet is a command-line check, not another service to run. Adapt the server command and flags to your setup.

LOCAL TERMINALbash
# Install from the repository
pip install git+https://github.com/devXyi/toolratchet

# Compare two saved tool surfaces
toolratchet diff tools.v1.json tools.v2.json --check-version
CI EXAMPLEyaml / shell
- uses: actions/checkout@v4
- uses: actions/setup-python@v5
  with:
    python-version: "3.12"
- run: pip install toolratchet
- run: toolratchet check -- python my_server.py

The commands are examples, not a copy-paste guarantee for every project. Check the README for supported inputs, capture options and CI output formats.

A deliberately conservative gate

A flag is a prompt to investigate, not a verdict that something is malicious. The goal is to make the change visible while a human can still make a decision.

04 — Boundaries

Useful checks are not a security guarantee.

We want the output to help a developer make a better decision, not imply that a clean report makes a tool safe.

What it can tell you

  • Which declared schemas and tool names changed.
  • Where token estimates grew beyond your budget.
  • Which text changes match configured risk heuristics.
  • Which differences deserve compatibility review.

What it cannot prove

  • That a server's runtime behavior stayed the same.
  • That a flagged description is malicious—or that unflagged text is safe.
  • That token estimates equal every model's actual tokenization.
  • That tests, permissions and runtime controls are unnecessary.
